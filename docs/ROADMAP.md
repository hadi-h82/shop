# نقشهٔ راه پروژه Sevart

## هدف این سند

این سند مسیر تبدیل Sevart از وضعیت فعلی به یک فروشگاه واقعی و قابل‌استفاده را نشان می‌دهد.

Roadmap دو بخش دارد:

1. **مسیر اصلی پروژه:** توضیح سادهٔ اینکه چه چیزی و با چه ترتیبی ساخته می‌شود.
2. **چک‌لیست فنی:** نکاتی که هنگام پیاده‌سازی هر مرحله باید بررسی شوند.

لازم نیست همهٔ جزئیات فنی از ابتدا تصمیم‌گیری یا هم‌زمان اجرا شوند. در هر مرحله فقط همان موضوع بررسی، پیاده‌سازی و تست می‌شود.

## قوانین ثابت پروژه

- هر بار فقط یک مرحله یا یک فایل تغییر می‌کند.
- مرحلهٔ بعد پس از تست و تأیید مرحلهٔ فعلی آغاز می‌شود.
- موجودی یا تعداد Stock به مشتری نمایش داده نمی‌شود.
- گزینه‌های محصول پویا و عمومی باقی می‌مانند.
- قیمت نهایی سفارش در Backend دوباره محاسبه می‌شود.
- سفارش، اطلاعات محصول و گزینه‌ها را به‌صورت Snapshot نگهداری می‌کند.
- رابط کاربری فارسی، RTL، Responsive و سازگار با Dark Theme باقی می‌ماند.
- از پیچیده‌کردن زودهنگام معماری خودداری می‌شود.

## وضعیت فعلی به زبان ساده

### بخش‌های موجود

- ساختار Angular، صفحات اصلی فروشگاه و SSR
- Backend چهارلایه با ASP.NET Core و EF Core
- Database اولیهٔ دسته‌بندی، محصول، تصویر و گزینه‌های محصول
- API مدیریت دسته‌بندی‌ها و محصولات
- پنل مدیریت دسته‌بندی و محصول
- گزینه‌های پویای محصول شامل Select، Radio و Color
- محاسبهٔ افزایش قیمت گزینه‌ها
- سبد خرید LocalStorage با حفظ گزینه‌های انتخاب‌شده
- صفحهٔ جزئیات محصول متصل به API
- صفحهٔ دسته‌بندی متصل به API

### بخش‌های نیمه‌کاره

- صفحهٔ خانه و فهرست همهٔ محصولات هنوز بخشی از داده را از Mock می‌گیرند.
- اطلاعات تصویر در Database ذخیره می‌شود، اما فایل تصویر واقعاً Upload نمی‌شود.
- فرم‌های ورود و ثبت‌نام فقط ظاهر و Validation اولیه دارند.
- Checkout هنوز سفارش واقعی ایجاد نمی‌کند.
- SSR هنگام Build ممکن است به API روی localhost وابسته شود.
- پنل مدیریت هنوز Authentication و دسترسی Admin ندارد.

### بخش‌های ساخته‌نشده

- آپلود واقعی تصویر
- Customer و Address
- Authentication و Authorization
- Order و OrderItem
- Shipping و Discount
- Payment
- مدیریت سفارش‌ها
- استقرار و Monitoring کامل Production

پنل مدیریت و API کاتالوگ روی یک ساختار Database مطمئن کار می‌کنند و اضافه‌شدن امکانات بعدی باعث بازطراحی غیرضروری نمی‌شود.

## مرحلهٔ ۲: آپلود و مدیریت تصویر محصول

### هدف

مدیر فروشگاه بتواند به‌جای واردکردن دستی URL، تصویر واقعی محصول را انتخاب و Upload کند.

### مسیر سادهٔ پیاده‌سازی

1. محل ذخیرهٔ تصاویر را انتخاب می‌کنیم.
2. Backend فایل را دریافت و بررسی می‌کند.
3. فایل با نام امن و یکتا ذخیره می‌شود.
4. آدرس تصویر به `ProductImage` متصل می‌شود.
5. پنل مدیریت امکان انتخاب و Upload فایل را می‌گیرد.
6. تصویر Uploadشده در Storefront نمایش داده می‌شود.
7. سپس حذف، ترتیب تصاویر و انتخاب تصویر اصلی تکمیل می‌شود.
8. در مرحلهٔ تکمیلی، حجم و ابعاد تصاویر بهینه می‌شوند.

### نسخهٔ اولیه‌ای که کافی است

- Upload فرمت‌های تصویری مجاز
- محدودیت حجم فایل
- تولید نام یکتا
- ثبت URL در محصول
- Preview و نمایش خطای Upload
- انتخاب تصویر اصلی
- حذف تصویر

### مواردی که می‌توانند بعداً تکمیل شوند

- تبدیل خودکار به WebP یا AVIF
- ساخت Thumbnail در چند اندازه
- CDN
- Upload مستقیم به Object Storage
- پردازش تصویر در Background Job

### نتیجهٔ قابل مشاهده

مدیر از داخل فرم محصول چند تصویر واقعی بارگذاری می‌کند، تصویر اصلی را تعیین می‌کند و تصاویر در فروشگاه نمایش داده می‌شوند.

# بخش دوم: چک‌لیست فنی هر مرحله

این بخش مرجع توسعه است. فقط هنگام رسیدن به همان مرحله از آن استفاده می‌کنیم.

## چک‌لیست فنی Catalog و Database

- FK و Delete Behaviorها
- Unique Constraint برای Slug محصول و دسته‌بندی
- Indexهای Status، Category و DisplayOrder
- Precision قیمت و `PriceAdjustment`
- Required و Optional بودن فیلدها
- رابطهٔ Product، Option Definition، Option و Value
- Validation استاندارد Requestها
- قرارداد یکسان خطاهای API
- تست رفتارهای مهم Domain

## چک‌لیست فنی آپلود تصویر

- abstraction ذخیره‌سازی مانند `IFileStorage`
- انتخاب Storage برای Development و Production
- Upload Endpoint
- محدودیت اندازه و تعداد تصاویر
- بررسی Extension، MIME Type و File Signature
- بررسی ابعاد تصویر
- نام‌گذاری تصادفی و امن
- جلوگیری از Path Traversal
- ثبت URL و metadata در `ProductImage`
- سازگاری عملیات Database و Storage
- حذف فایل‌های بدون رکورد و رکوردهای بدون فایل
- Preview، Progress و Error در Admin
- انتخاب تصویر اصلی و ترتیب نمایش
- حذف و جایگزینی کنترل‌شده
- Resize و فرمت بهینهٔ وب
- Cache Policy و CDN در صورت نیاز
- نگهداری Credential فقط در Backend

## چک‌لیست فنی Frontend و API

- API عمومی فقط Product منتشرشده و Category فعال را برگرداند.
- Option و Value غیرفعال در پاسخ عمومی دیده نشوند.
- Pagination، Sort، Filter و Search قرارداد مشخص داشته باشند.
- Mapping پاسخ API به مدل UI متمرکز باشد.
- Loading، Empty و Error State استاندارد باشند.
- Route جزئیات محصول از Slug استفاده کند.
- Mock فقط بعد از حذف همهٔ وابستگی‌ها پاک شود.

## چک‌لیست فنی SSR و SEO

- Render Mode هر Route مشخص باشد.
- Production Build به API محلی وابسته نباشد.
- دسترسی به Browser APIها SSR-safe باشد.
- Hydration Error وجود نداشته باشد.
- Site URL از Configuration واحد خوانده شود.
- Canonical، Metadata، Sitemap، Robots و 404 بررسی شوند.

## چک‌لیست فنی Authentication

- Password Hashing امن
- Session یا Token Strategy مشخص
- Role و Policy برای Admin و Customer
- محافظت هم‌زمان Frontend و Backend
- انقضا و لغو Credential
- Rate Limit برای Login و بازیابی رمز
- عدم ذخیرهٔ Secret حساس در مرورگر

## چک‌لیست فنی سفارش و پرداخت

- Snapshot نام و قیمت محصول
- Snapshot نام گزینه، مقدار و `PriceAdjustment`
- محاسبهٔ قیمت در Backend
- Transaction ثبت سفارش
- جلوگیری از سفارش یا پرداخت تکراری
- ثبت Payment Attempt
- Verify پرداخت در Backend
- مدیریت Callback تکراری
- ثبت تاریخچهٔ تغییر وضعیت سفارش

## چک‌لیست فنی Production

- Environment و Secret Management
- CORS محیط‌محور
- Global Exception Handling
- Logging و Correlation ID
- Health Check
- Rate Limiting
- Migration و Rollback Plan
- Backup و Restore Test
- Cache و Image Optimization
- Monitoring و Alerting
- تست امنیت Admin و Checkout

## مواردی که فعلاً لازم نیستند

- Microservice Architecture
- Message Broker بدون نیاز واقعی
- Marketplace چندفروشنده
- Recommendation Engine پیچیده
